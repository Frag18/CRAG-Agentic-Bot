# System Design: NIST AI RMF Agentic RAG System

This document provides a comprehensive technical breakdown of the architectural decisions, data engineering pipelines, vector retrieval mechanisms, and stateful agentic workflows implemented in this repository.

---

## 1. How You Split the Documents and Why

### The Structural Reality of NIST Publications
Official policy publications like the **NIST AI Risk Management Framework (AI RMF 1.0, NIST AI 100-1)** and the **Generative AI Profile (NIST AI 600-1)** present acute structural challenges for conventional chunking approaches:
1. **Multi-Page Policy Tables**: In NIST AI 100-1, Tables 1–4 (Core Functions: GOVERN, MAP, MEASURE, MANAGE) span pages 27–34. Category headers (e.g. `GOVERN 4: Organizational teams are committed...`) appear only in the first row on page 28; subsequent rows on page 29 feature blank category cells. Naive character or token chunkers slice rows in half, strip headers, or leave subcategory rows without their governing parent text.
2. **Action-Row Matrices**: NIST AI 600-1 contains 211 specific action rows (GV, MP, MS, MG) across pages 35–64. Each row maps an Action ID (e.g. `MG-3.2-001`) to suggested actions, targeted GAI risks (e.g. *Harmful Bias and Homogenization*), and AI actor tasks.
3. **Typography & Heading Hierarchies**: Important policy provisions are structured hierarchically (`Part > Section > Category > Subcategory`). Arbitrary token splits cut across heading boundaries, causing prose to lose its governing context.
4. **Complex Diagrammatic Figures**: Crucial conceptual structures (e.g., Fig. 1 Harms, Fig. 4 Trustworthiness Characteristics, Fig. 5 Core Functions wheel) are visual diagrams. Figure 3 is a landscape-oriented page on PDF page 16 (printed p.11). Standard text extraction ignores them entirely.

### Two-Stage Deterministic Ingestion Pipeline

To solve this without hallucination or information loss, the pipeline in [`src/parse_pdf.py`](file:///d:/assignment_whitecrowresearch/src/parse_pdf.py) and [`src/ingest.py`](file:///d:/assignment_whitecrowresearch/src/ingest.py) uses a two-stage extraction process:

```
                  [ Official NIST PDFs ]
                            │
                            ▼
          ┌───────────────────────────────────┐
          │     PyMuPDF + pdfplumber          │  (src/parse_pdf.py)
          │  - Typography & heading parsing   │
          │  - Running header/footer strip    │
          │  - Multi-page table reconstruction│
          │  - 200 DPI landscape rotation     │
          └─────────────────┬─────────────────┘
                            │
               ┌────────────┴────────────┐
               ▼                         ▼
      [ Structured Markdown ]   [ Extracted Tables & Figures ]
      - nist_ai_rmf_1.0.md      - 72 Subcategory rows (Tables 1-4)
      - nist_ai_rmf_genai.md    - 211 Action rows (Appendix B)
               │                - 5 Figure visual descriptions
               │                         │
               ▼                         │
     ┌───────────────────┐               │
     │   LlamaIndex AST  │ (src/ingest.py)│
     │ MarkdownNodeParser│               │
     │ SentenceSplitter  │               │
     └─────────┬─────────┘               │
               │                         │
               └────────────┬────────────┘
                            │
                            ▼
               [ Exactly 588 Atomic Nodes ]
               - 72 Core Subcategory Nodes
               - 211 GenAI Action Nodes
               - 5 Figure Multimodal Nodes
               - 300 Section-Grounded Prose Nodes
```

#### Stage 1: Deterministic Parsing & Table Reconstruction (`src/parse_pdf.py`)
- **Engine**: Built exclusively using **PyMuPDF (`fitz`)** and **`pdfplumber`** (zero LlamaIndex readers or LlamaParse).
- **Header & Footer Hygiene**: Eliminates running headers (`y < 52`) such as `NIST AI 100-1` and `AI RMF 1.0`, and strips bare printed page footers (`y > 705`) to prevent false keyword matches and glued words.
- **Hyphenation Repair**: Uses regex passes to rejoin broken words across line wraps (e.g. `inte- grated` $\rightarrow$ `integrated`, `or- ganizational` $\rightarrow$ `organizational`).
- **Table Reconstruction & Forward-Filling**: `pdfplumber` extracts cell grids across page breaks. It automatically forward-fills merged category text down empty cells so every subcategory chunk is completely autonomous and retains its governing category title.
- **Rotated Multimodal Figures**: Extracts Figures 1 through 5. Figure 3 is rotated 90° clockwise before rendering at 200 DPI. High-fidelity descriptions generated by Gemini Vision are cached deterministically in `data/parsed/figures.json`.

#### Stage 2: Heading-Aware Node Parsing via LlamaIndex (`src/ingest.py`)
- **Strict Boundary**: *LlamaIndex is strictly confined to `src/ingest.py` for node parsing and is never imported into graph, nodes, edges, state, or retrieval modules.*
- **AST Section Splitting**: Uses `MarkdownNodeParser` so chunks **never cross a heading boundary** (`#`, `##`, `###`).
- **Sentence Splitting**: Within long prose sections, `SentenceSplitter(chunk_size=160 tokens, chunk_overlap=30 tokens)` splits long text along sentence boundaries within token limits.
- **Navigation Breadcrumbs**: Every node prepends a navigation breadcrumb (e.g. `NIST AI RMF 1.0 > Part 2: Core and Profiles > 5.1 Govern > GOVERN 4 > GOVERN 4.2:`).
- **Result**: Exactly **588 atomic, searchable chunks** preserving 100% of the original documents without orphaned sentences or broken tables.

## 2. Why You Selected Your Embedding Model and Vector Store

### Dense Embedding Model: `sentence-transformers/all-MiniLM-L6-v2`
1. **Zero Cost & Local CPU Execution**:
   - `all-MiniLM-L6-v2` runs locally via HuggingFace transformers (`HF_HUB_OFFLINE=1`).
   - Generates 384-dimensional dense vectors in milliseconds on standard CPU hardware without GPU requirements.
   - Eliminates external embedding API costs, network latency, and third-party rate limiting (HTTP 429).
2. **High Semantic Density for Technical Prose**:
   - Despite its compact footprint (80 MB), MiniLM is trained via knowledge distillation on over 1 billion sentence pairs, yielding strong semantic clustering for technical policy queries.
3. **Drop-In Extensibility**:
   - Handled dynamically via `src/config.py`: developers can switch to `BAAI/bge-small-en-v1.5` or OpenAI `text-embedding-3-small` simply by updating `.env`.

### Vector Store: `langchain_chroma.Chroma`
1. **Native Local Persistence**:
   - Chroma provides lightweight embedded persistence in `./chroma_db` using SQLite and HNSW vector indices, requiring no external server processes, Docker containers, or cloud accounts.
2. **Rich Metadata Filtering**:
   - Stores rich structured metadata per chunk:
     ```python
     {
         "document_name": "NIST AI RMF Generative AI Profile",
         "doc_id": "ai_rmf_genai",
         "node_type": "action_row",
         "action_id": "MG-3.2-001",
         "function": "MANAGE",
         "pdf_page": 47,
         "printed_page": 43,
         "section_title": "3. Suggested Actions to Manage GAI Risks"
     }
     ```
3. **Zero-Pollution Test Isolation**:
   - Unit and integration tests (`tests/test_ingestion.py` and `tests/test_pipeline.py`) instantiate temporary on-the-fly Chroma instances (`tempfile.mkdtemp()`) that are destroyed upon test teardown. The production `./chroma_db` is never polluted.

## 3. How Retrieval Works

### Tri-Tier Hybrid Retrieval Architecture (`src/vector_store.py`)
Vector similarity search alone struggles with alphanumeric identifiers (e.g. `MG-3.2-001` or `MEASURE 2.11`) because embedding models dilute specific numeric codes into general semantic space. Our solution fuses dense semantic search, sparse lexical search, and deterministic regex routing:

```
                          User / Standalone Query
                                     │
                                     ▼
                         [ HybridRetriever.invoke ]
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         ▼                           ▼                           ▼
  [ Exact-ID Shortcut ]      [ Chroma Dense Search ]     [ BM25 Keyword Search ]
  (Regex matches on          (Cosine similarity over     (BM25Okapi scoring over
  Action ID, Subcategory,     MiniLM dense vectors)       in-memory corpus)
  Category, Figure, etc.)            │                           │
         │                           └─────────────┬─────────────┘
         │                                         │
         │                                         ▼
         │                             [ EnsembleRetriever ]
         │                         (Weights: 0.5 Dense, 0.5 BM25)
         │                                         │
         └────────────────►─────────┬──────────────┘
                                    │
                                    ▼
                       [ Deduplicate & Rank Top-k ]
                 (Exact matches at index 0, followed by
                   ensemble results, capped at k=6)
```

1. **Exact-ID Regex Priority Shortcut**:
   - Evaluates fast regex checks before search:
     - **Action IDs**: `r"\b([A-Z]{2}-\d+\.\d+-\d{3})\b"` (e.g. `MG-3.2-001`, `GV-1.1-002`)
     - **Subcategories**: `r"\b((?:GOVERN|MAP|MEASURE|MANAGE)\s+\d+\.\d+)\b"` (e.g. `MEASURE 2.11`)
     - **Categories**: `r"\b((?:GOVERN|MAP|MEASURE|MANAGE)\s+\d+)\b"` (e.g. `GOVERN 4`)
     - **Figures**: `r"\b(?:Fig(?:ure|\.)?)\s*(\d+)\b"`
   - When matched, the exact document chunk is hoisted directly to **Index 0** in the returned candidates list.
2. **Dense Semantic Search**:
   - Runs cosine similarity search against ChromaDB ($k=6$). Captures conceptual meaning (e.g., *"How do we manage bias in machine learning models?"*).
3. **Sparse Lexical Search (`BM25Okapi`)**:
   - Searches an in-memory inverted index of all 588 documents (`data/parsed/corpus.pkl`). Captures exact terminology and acronyms (e.g., `TEVV`, `CBRN`, `confabulation`).
4. **Reciprocal Rank Fusion**:
   - Merges dense and sparse ranks via `EnsembleRetriever(weights=[0.5, 0.5])`.
   - Deduplicates chunks by `chunk_id` and emits the top 6 most relevant documents.

## 4. How You Structured the LangGraph Workflow

### State Machine Architecture (`src/graph.py`)
Rather than using a rigid linear chain, the RAG pipeline is modeled as a stateful, cyclic finite state machine (**Corrective RAG / CRAG**) compiled via `langgraph.graph.StateGraph`.

```
                        User Input
                            │
                            ▼
               ┌───────────────────────────┐
               │    contextualize_query    │  <── Resolves follow-ups (history capped to 6 turns)
               └─────────────┬─────────────┘
                             │
                     [ check_input_guard ]
                      /                 \
         (Meaningful query)            (Trivial query: <3 words, "?", "hi")
                    │                                    │
                    ▼                                    ▼
       ┌───────────────────────────┐       ┌─────────────────────────────┐
       │         retrieve          │       │ handle_insufficient_context │ ──► [ END ]
       └─────────────┬─────────────┘       └─────────────────────────────┘     (Sources: None,
                     │                                                          0 LLM calls)
                     ▼
       ┌───────────────────────────┐
       │      grade_documents      │  <── 1 Batched LLM call returning {"relevant_indices": [...]}
       └─────────────┬─────────────┘      with exponential backoff on 429/5xx errors
                     │
                     ▼
            [ decide_to_generate ]
             /         │         \
 (Sufficient)          │          (Insufficient & Retries Exhausted)
       ▼               │                       ▼
┌──────────────────┐   │         ┌─────────────────────────────┐
│ generate_answer  │   │         │ handle_insufficient_context │
└─────────┬────────┘   │         └──────────────┬──────────────┘
          │            │                        │
          │            ▼                        │
          │  (Insufficient & Retries < 1)       │
          │  ┌──────────────────┐               │
          │  │  rewrite_query   │ ──────────────┘ (Loops back to retrieve without
          │  └──────────────────┘                  injecting ungrounded terms)
          ▼
      [  END  ]
```

### The 6 Core Nodes (`src/nodes.py`)
1. **`contextualize_query`**: Inspects message history to rewrite pronouns and conversational references into a self-contained question. Bypasses the LLM when no history exists.
2. **`retrieve`**: Invokes the hybrid retriever with exact-ID shortcuts.
3. **`grade_documents` (Single-Call Batched Grading)**:
   - Evaluates all retrieved candidate chunks in **ONE batched LLM call** using structured JSON output: `{"relevant_indices": [0, 2]}`.
   - Reduces token overhead and latency by 83% compared to evaluating chunks individually.
   - Protected with `tenacity` exponential backoff retries (`min=2s, max=10s`) for resilience against HTTP 429 rate limits.
4. **`rewrite_query`**: Formulates an expanded query when retrieved context fails relevance grading. Strictly prohibited from hallucinating external acronyms.
5. **`generate_answer`**: Synthesizes the grounded answer. Mandates an inline token: `Used Chunks: [index1, index2]` so that only chunks actually contributing to the synthesis are cited.
6. **`handle_insufficient_context`**: Deterministic refusal handler that sets `sources = []` (rendering `Sources: None`) with **0 LLM calls**.

### The Conditional Edges (`src/edges.py`)
- **`check_input_guard`**: Intercepts trivial queries (`?`, `hi`, empty strings, or fewer than 3 words) before retrieval. Routes immediately to refusal, executing in **< 10ms with 0 LLM calls**.
- **`decide_to_generate`**: Routes to `generate_answer` if relevant documents exist. If 0 relevant documents exist, loops to `rewrite_query` if `retry_count < MAX_RETRIES` (default 1); otherwise routes to `handle_insufficient_context`.

## 5. How You Handle Insufficient or Irrelevant Context

To satisfy the strict requirement that out-of-scope or adversarial queries must **never hallucinate answers or invent fake sources**, the system applies a 3-tier defense-in-depth model:

### Tier 1: Zero-Call Input Guard (`src/edges.py`)
- Queries consisting solely of punctuation (e.g. `?`, `!`), greetings (`hi`, `hello`), or trivial word counts without question words bypass retrieval and LLMs completely.
- Response: `"Please ask a question about the NIST AI RMF documents."`
- Sources: `None`.

### Tier 2: Batched Relevance Grader & CRAG Loop (`src/nodes.py`)
- When a user asks an ungrounded out-of-scope question (e.g., *"How do I bake a chocolate cake?"* or *"What is GPT-5 pricing?"*), vector search may retrieve nearest neighbors based on superficial token overlap.
- The batched relevance grader evaluates each chunk against the query.
- When 0 chunks pass relevance grading:
  1. The pipeline attempts one query rewrite (`rewrite_query`).
  2. The rewritten search fails again.
  3. `decide_to_generate` detects `retry_count >= 1` and diverts execution away from the generator to `handle_insufficient_context`.

### Tier 3: Generator `NO_INFO:` Contract (`src/nodes.py`)
- If ambiguous chunks slip past the grader, the generation prompt enforces a strict negative constraint:
  ```text
  CRITICAL INSTRUCTION:
  If the provided context does NOT contain sufficient facts to answer the question,
  you MUST start your response with the exact prefix 'NO_INFO:' followed by a brief explanation.
  Do NOT attempt to guess, extrapolate, or use outside pre-training knowledge.
  ```
- When `generate_answer` detects the `NO_INFO:` prefix, it discards the text and emits the standardized refusal:
  ```text
  Answer:
  I could not find sufficient information in the official NIST AI Risk Management Framework (AI RMF 1.0) or the Generative AI Profile (NIST AI 600-1) to answer your question.

  Sources:
  - None
  ```
- **Programmatic Attribution**: Citations are derived exclusively from document metadata (`printed_page` and `pdf_page`), never hallucinated by the model.

## 6. How Conversational Context is Maintained

### State Representation
Conversational state is stored as a list of LangChain message objects in `GraphState["messages"]` using functional append reducers (`operator.add`).

### Contextual Query Disambiguation (`src/nodes.py`)
When a user asks follow-up questions with pronouns or missing subjects (e.g., Turn 1: *"What are the four functions?"*, Turn 2: *"Which one is cross-cutting?"*, Turn 3: *"What are its subcategories?"*), the query cannot be directly passed to vector search.
- The `contextualize_query` node feeds the conversation history to the LLM with a dedicated prompt:
  *"Formulate a standalone question which can be understood without the conversation history."*
- Rewrites Turn 2 into: *"Which function of the NIST AI Risk Management Framework is designed to be cross-cutting?"*
- Rewrites Turn 3 into: *"What are the subcategories of the GOVERN function in the NIST AI RMF?"*

### Preventing Context Bleed & Memory Pollution
Multi-turn systems often suffer from context contamination across conversation turns. We enforce two strict architectural protections:
1. **Source Stripping from Prior Turns**:
   Before prior assistant messages are passed to the contextualizer LLM, all trailing `Sources:` blocks are stripped via regex:
   ```python
   clean_content = re.sub(
       r"\n\s*(?:Sources|Citations):[\s\S]*$", 
       "", 
       msg.content, 
       flags=re.IGNORECASE
   ).strip()
   ```
   This prevents old citations and page numbers from leaking into subsequent queries.
2. **Bounded Windowing (`MAX_HISTORY_TURNS = 6`)**:
   Only the 6 most recent turns are retained for query contextualization, ensuring prompt tokens remain bounded and avoiding semantic drift.
3. **Clean Topic Switching**:
   If the user transitions from one topic to an entirely unrelated topic (e.g., from trustworthiness characteristics to *"Now, completely different: what is confabulation?"*), the contextualizer recognizes the explicit break and outputs a clean standalone query targeting Section 2.2 without carrying forward stale keywords.

## 7. High-Availability Provider Architecture & Resilience

```
                    LangGraph Workflow Node
                               │
                               ▼
                    [ Dual-Provider LLM Chain ]
                  primary.with_fallbacks([fallback])
                               │
               ┌───────────────┴───────────────┐
               ▼                               ▼
       [ Google Gemini ]                 [ Groq LLM ]
    Primary: gemini-2.0-flash-lite    Fallback: openai/gpt-oss-120b
    (Fast, high rate-limits)          (Ultra-fast open-weight failover)
```

- **Transparent Failover**: Handled via `primary_llm.with_fallbacks([fallback_llm])`. If Gemini encounters an outage or rate limit (HTTP 429), the invocation automatically and transparently executes on Groq without user interruption.
- **Deterministic Mock Mode**: If neither API key is provided, the system defaults to a deterministic local regex evaluator, allowing automated unit tests to pass without API credentials.

## 8. Summary of Known Trade-Offs

1. **Local Embeddings vs. Cloud API Embeddings**: `all-MiniLM-L6-v2` offers 384 dimensions vs. OpenAI's 1536 dimensions. Paired with BM25 and exact-ID shortcuts, it achieves 100% recall on technical identifiers while maintaining zero latency overhead and zero cost.
2. **Ensemble Retrieval vs. Heavy Cross-Encoder Reranker**: The hybrid retriever blends dense and BM25 scores using reciprocal rank fusion `[0.5, 0.5]`. A heavy cross-encoder (e.g. Cohere or BGE reranker) was omitted to keep end-to-end query latency under 1.5 seconds.
3. **Bounded CRAG Loop**: The retry counter is capped at `MAX_RETRIES=1` to guarantee bounded latency and eliminate cyclic hallucination.
